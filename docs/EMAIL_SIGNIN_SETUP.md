# Email delivery and sign-in setup

The configured sender addresses are `gokulkangeyan@gmail.com` (primary) and `gokulsenthilkumar3@zohomail.in` (secondary). A sender address does not establish domain ownership or provide SMTP authorization. No passwords belong in this document, Git, screenshots, or chat.

## Gmail

1. Enable Google 2-Step Verification in the account that owns the Gmail address.
2. Open https://myaccount.google.com/apppasswords and generate an app password named EverGreen. Availability depends on the account's security and administrator policies; see https://support.google.com/mail/answer/185833.
3. From the EverGreen project folder, run the local setup command below. It asks for the app password with hidden input and saves it to the ignored API environment file. It preserves other environment settings and does not send email.

```powershell
powershell -NoProfile -File scripts/security/configure-smtp.ps1 -Sender primary
```

Alternatively, edit the environment file yourself:
Add the following to the API's local, ignored `apps/api/.env`, preserving its existing settings:

```dotenv
SMTP_PRIMARY_HOST=smtp.gmail.com
SMTP_PRIMARY_PORT=587
SMTP_PRIMARY_SECURE=false
SMTP_PRIMARY_USER=gokulkangeyan@gmail.com
SMTP_PRIMARY_FROM=gokulkangeyan@gmail.com
SMTP_PRIMARY_PASSWORD=YOUR_APP_PASSWORD
PUBLIC_APP_URL=http://localhost:4000
INVITE_TTL_HOURS=24
```

`SECURE=false` on port 587 uses required STARTTLS; it does not permit plaintext delivery. Use the app password, not the account's normal password. In production set `PUBLIC_APP_URL` to the actual authorized HTTPS application URL. Do not copy an arbitrary domain into it.

## Zoho

Find the account's exact SMTP host in Zoho Mail's account settings. Regional hosts and SMTP availability depend on the account. See https://www.zoho.com/mail/help/zoho-smtp.html. Create an application-specific password when required by the account's MFA policy.

Once you have that hostname and app password, run `powershell -NoProfile -File scripts/security/configure-smtp.ps1 -Sender secondary`. The command asks for the hostname and hides the password input.

```dotenv
SMTP_SECONDARY_HOST=smtp.zoho.in
SMTP_SECONDARY_PORT=465
SMTP_SECONDARY_SECURE=true
SMTP_SECONDARY_USER=gokulsenthilkumar3@zohomail.in
SMTP_SECONDARY_FROM=gokulsenthilkumar3@zohomail.in
SMTP_SECONDARY_PASSWORD=YOUR_ZOHO_APP_PASSWORD
```

The host above is an example for the India region; use the value shown by the actual mailbox. Do not enter credentials into a different SMTP host. Port 465 uses TLS from connection start. Do not disable certificate checks.

Restart the existing API processes with `npm run owner:start` after configuring credentials. Open Users → Invitations to see whether each sender is configured. Use **Test SMTP connection** for the selected sender; it authenticates to the server without sending a message. Configuration presence alone is not a successful connection or delivery. A real invitation is a real email: choose the intended recipient yourself. SMTP acceptance does not prove inbox delivery, opening, or invitation completion. Sender choice is explicit; the app does not automatically retry using another mailbox after an ambiguous delivery failure.

Using existing mail accounts does not require buying a custom domain or an identity provider. Sending limits and plan restrictions still apply. An app password must be generated by the account owner; the application cannot generate one from an email address.

## SMTP versus OIDC

SMTP delivers messages. OpenID Connect (OIDC) authenticates people through a provider such as Google, Microsoft Entra, or a self-hosted identity service. Configuring SMTP does not enable SSO.

Google is a reasonable starting provider for the supplied Gmail account. Enabling it requires an OAuth client ID, client secret where applicable, and an exact authorized callback URL in a Google Cloud project you control. A Zoho mailbox is not automatically a Google identity. A successful external login must still map to an explicitly authorized EverGreen account; email domains alone must not grant staff access.

EverGreen implements OIDC with PKCE, state, nonce, browser-bound completion and explicit account linking. Provider configuration and an end-to-end test are still required; local unit tests do not establish a working Google integration.

1. Sign in to https://console.cloud.google.com/ with the Google account that will own the integration. Create or select a project. No custom domain is needed for the localhost development flow.
2. Open Google Auth Platform. Configure the application's branding and audience. For personal Gmail use an external audience; while testing, add the Google accounts that will test sign-in as test users if required by the console.
3. In Clients create an OAuth client of type **Web application**. Add this exact authorized redirect URI: `http://localhost:4000/api/backend/auth/oidc/callback`. Do not substitute port 4301: this flow uses the application's browser proxy so the callback has the same origin as the browser cookie.
4. Save the client ID and secret locally in `apps/api/.env`:

```dotenv
OIDC_ISSUER=https://accounts.google.com
OIDC_LABEL=Google
OIDC_CLIENT_ID=YOUR_WEB_CLIENT_ID
OIDC_CLIENT_SECRET=YOUR_CLIENT_SECRET
OIDC_CALLBACK_URL=http://localhost:4000/api/backend/auth/oidc/callback
```

5. Restart the APIs. Sign in to EverGreen with your existing password first, open Security Settings → Linked sign-in identities, and link the Google identity you control using your current password and authenticator code when enabled. Then test signing out and signing in with the provider. Matching email addresses do not auto-link or grant access.
6. For deployment, register the exact HTTPS callback on the domain you control and update `PUBLIC_APP_URL` plus `OIDC_CALLBACK_URL`. Review the provider's publishing/verification requirements before allowing public use. This setup requests only `openid email profile`; it does not authorize Gmail SMTP, send email, or provide SAML support.

Google's setup reference: https://developers.google.com/identity/openid-connect/openid-connect. Leave the client credentials empty until registration is complete; EverGreen then keeps provider sign-in unavailable.
